## 3. Near-duplicates

### Configuration

The production pipeline uses MinHash with 128 permutations and Locality-Sensitive Hashing (LSH) with 16 bands and 8 rows per band. The configured near-duplicate similarity threshold is `0.80`. Documents shorter than 30 characters are handled using exact deduplication only.

Near-duplicate detection helps remove repeated or highly similar documents while retaining useful training examples. However, similarity alone can incorrectly identify distinct documents as duplicates when they share a common structure or template.

### Manual review methodology

For manual review, `tools/dedup_review.py` examined **15,950 documents** and identified **1,049,616 candidate pairs** using a looser LSH configuration of 32 bands and 4 rows. The tool then calculated exact Jaccard similarity over character shingles and printed sampled pairs from different similarity ranges.

The candidate-pair counts were:

| Jaccard similarity range | Candidate pairs |
|---|---:|
| 0.50–0.60 | 101,024 |
| 0.60–0.70 | 183,933 |
| 0.70–0.80 | 355,572 |
| 0.80–0.90 | 229,240 |
| 0.90–1.00 | 13,126 |

These counts describe the manual review tool's candidate pairs, not the number of documents removed by the production pipeline. The review samples pairs for inspection; it does not manually verify every candidate pair.

### Review observations

The sampled pairs revealed that Hindi Wikipedia year pages can have high textual similarity even when they describe different years. These pages often share headings such as `घटनाएँ`, `जन्म`, and `निधन`, along with a similar calendar-year structure.

The following examples illustrate this limitation:

1. **Jaccard similarity: 0.786**
   - Document IDs: `c33abcb794073f54` and `1dc363423cd5d2c7`
   - The excerpts describe the years 678 and 1111.
   - **Decision: Keep both.** The pages describe different years despite their shared structure.

2. **Jaccard similarity: 0.791**
   - Document IDs: `748ad8638a4277ef` and `e13c351188e03f6a`
   - The excerpts describe the years 558 and 966.
   - **Decision: Keep both.** The shared calendar-year template does not make the year-specific content a duplicate.

3. **Jaccard similarity: 0.791**
   - Document IDs: `df4f44665f3bab3a` and `8e77267b27ab5ca7`
   - The excerpts describe the years 817 and 826.
   - **Decision: Keep both.** The pages share headings and structure but refer to different years.

4. **Jaccard similarity: 0.853**
   - Document IDs: `4246a1fc65daffec` and `0b3af9d66dac39c7`
   - The excerpts describe the years 733 and 1406.
   - **Decision: Keep both based on the reviewed excerpts.** This example shows that even high similarity can arise from a shared template rather than duplicate meaning.

These are sampled manual-review examples. They do not establish whether these particular pairs were removed by the production pipeline.

### Confirmed production false positive

Inspection of an actual production near-duplicate record confirmed one false positive:

- **Dropped document ID:** `7091244e660c9919`
- **Matched document ID:** `24018d7ac5d46b81`
- **Recorded similarity:** `0.828`
- **Dropped text:** `गजपति भारत के उड़ीसा प्रान्त का एक जिला है।`
- **Matched text:** `रायगढा भारत के उड़ीसा प्रान्त का एक जिला है।`

Both documents describe different districts in Odisha, India. Their sentence structures are almost identical, but their factual referents differ. The Gajapati document was dropped as a near-duplicate of the Rayagada document.

**Manual decision: retain both documents.** This is a confirmed false positive in the inspected production example. It demonstrates that character-based similarity can remove distinct factual information when documents share a template.

This single example does not establish the overall false-positive rate. Additional production removals should be inspected to determine how frequently this occurs.

### Threshold decision

The review demonstrates that character-shingle similarity alone cannot reliably distinguish duplicate documents from distinct records that share a template. A threshold of `0.80` is the current configured value, but the manual review does not establish that it is optimal.

Before changing the threshold, the actual production near-duplicate removals should be inspected. A stronger approach would combine similarity scoring with template-aware checks, particularly for highly structured Wikipedia pages such as year articles and short factual descriptions.

### Filter configuration and decision

The repetition filter is configured with the following values:

- `REPEAT_MIN_TOKENS = 10`
- `REPEAT_TOP_SHARE = 0.40`
- `REPEAT_UNIQUE_RATIO = 0.15`

The filter checks repetition when a document has at least 10 tokens. It flags text when the most frequent token accounts for more than 40% of tokens or when the ratio of unique tokens to total tokens is below 15%.

The reviewed mathematical Hinglish example illustrates a limitation of generic repetition rules: a frequently repeated number can be legitimate in an educational explanation. However, the sample is too small to justify changing the thresholds globally.

Deliberate non-rules include avoiding a blanket minimum-length rule that could discard proverbs or couplets and requiring a minimum token count before applying repetition checks. Further review should inspect additional removed records and test any proposed changes against both noisy text and legitimate Hindi/Hinglish examples.

## 5. Contamination

The evaluation set contains 200 held-out passages, including 60 Hinglish items. The selection uses a deterministic seed and document identifiers. The evaluation set is intended to assess performance on held-out Hindi/Hinglish text; it is not, by itself, a complete benchmark of language-model quality.

The contamination checks use:

1. Exact matching against evaluation text.
2. Normalized matching after case and punctuation/whitespace normalization.
3. Near-match detection using word 4-gram containment.
4. Cross-script matching using a reduced consonant skeleton and 7-gram shingles for Devanagari and romanized Hindi.

The run reported **43 evaluation items affected by potential contamination** and **1,559 training documents removed** by the contamination stage.

The pipeline also records candidate matches in `data/output/contamination.jsonl` and rejected candidates in `data/output/contamination_rejected.jsonl`.

### Remaining contamination review

The per-method match counts have not yet been verified. Before final submission, inspect the output files and record the actual counts for exact, normalized, near, and cross-script matches. Do not infer those per-method counts from the total alone.

Also inspect at least one rejected candidate and record:

- Evaluation document ID.
- Training document ID.
- Match method and recorded score.
- Relevant text excerpts.
- Why the match is considered a true leak or a false positive.

**Limitation:** Matching operates on normalized text, so exact matching means exact under the pipeline's normalization, not necessarily byte-for-byte identity of the original source text.

Cross-script similarity is heuristic and can produce false positives. Manual inspection is necessary before interpreting every detected match as a genuine leak.

### Manual review of contamination candidates

Inspection of `contamination_rejected.jsonl` found near-match candidates involving distinct Wikipedia pages with shared template language. For example, the evaluation item about Kannauj district was matched against training text about Katihar, Khagaria, Gaya, and other Bihar districts, with near-match scores around 0.312–0.385. Another example matched the Palwal city evaluation item against Kishanganj and Khagaria city pages with a score of 0.529.

These examples appear to be false positives caused by common encyclopedia sentence structures rather than identical underlying content. They demonstrate a limitation of similarity-based contamination detection: pages describing different places can share substantial wording. The examples were inspected as rejected candidates; they should not be interpreted as confirmed contamination or as proof that all flagged pairs are false positives.

## 6. Reproducibility

The pipeline is run using:

```bash
./run.sh data/raw data/output
```

The run used Python 3.11.4. The repository includes `requirements.txt`, a deterministic evaluation seed, document identifiers derived from source/path/ordinal information, and a manifest recording input file sizes and SHA-256 hashes.

The manifest records the source metadata, pipeline counts, and configuration used for the run. The current manifest reports `git_commit: null`, so the run is not yet tied to a recorded Git commit.

The Wikipedia download procedure is not fully pinned to a fixed source revision. Reproduction should therefore use the archived raw files and verify their SHA-256 hashes rather than assuming a future download will return identical bytes.

Before claiming byte-identical reproducibility, run the pipeline twice against the same raw inputs and configuration, compare output hashes, and record the actual result. Passing unit tests alone does not establish byte-identical output.

The current automated test result is **13 tests passed**. This demonstrates that the tested cases pass; it does not independently establish full reproducibility or correctness for every input.

## 7. Scale: 2 TB of data on object storage

The current implementation is a prototype and is not yet suitable for processing 2 TB of data in its current form.

The main scaling concern is global state in stage B: exact-deduplication structures and near-duplicate indexes consume memory as the corpus grows. Stage A also processes the available input files sequentially rather than distributing work across a cluster.

A scalable design would:

- Process independent files or byte ranges in parallel.
- Store intermediate results in partitioned object storage.
- Partition deduplication candidates by hash/LSH keys and perform distributed comparisons.
- Use a distributed or external index for contamination checks.
- Keep evaluation data and its matching index small enough to broadcast where appropriate.
- Track checkpoint state and content hashes so interrupted jobs can resume safely.
- Write outputs through a validated, atomic publication step.

These are proposed improvements, not capabilities demonstrated by the current run. The existing prototype should be profiled and redesigned before claiming that it can process 2 TB within a specific time or memory budget.
